### 1. The Architecture: Engine vs. Web APIs

**Direct Answer:** JavaScript is a single-threaded language, meaning it has only one **Call Stack** and can only execute one task at a time. However, the JavaScript Engine (like V8) does not contain everything. Features like `setTimeout`, `fetch`, and the `DOM` are not part of the JavaScript language itself; they are **Web APIs** provided by the browser. These APIs act as separate threads that handle long-running tasks in the background, allowing the Call Stack to remain clear and non-blocking.

**Example: Offloading to the Browser**

```js
console.log("Step 1");
setTimeout(() => console.log("Step 2"), 1000);
console.log("Step 3");
```

**Code Explanation:**

- `console.log("Step 1");`: This is synchronous code. It is pushed onto the **Call Stack**, executed, and then immediately popped off.
- `setTimeout(...)`: This is a **Web API**. JavaScript pushes it to the stack, but all it does is register the callback and the 1000ms delay with the browser’s timer API. Once registered, it is popped off the stack instantly—it does **not** wait for the timer to finish.
- `console.log("Step 3");`: This runs immediately after the timer is registered. The stack is empty, so it executes and pops off.
- **Connection:** The browser handles the 1000ms countdown in the background, leaving the main JavaScript thread free to continue.

### 2. The Task Queue (Callback Queue)

**Direct Answer:** When a callback-based Web API (like a timer or geolocation) finishes its background task, it cannot jump straight back onto the Call Stack. Instead, it enters the **Task Queue**. The **Event Loop** is the "gatekeeper" that watches the Call Stack. It only moves a task from the queue to the stack when the stack is completely empty.

**Example: Minimum Delay vs. Guaranteed Delay**

```js
setTimeout(() => console.log("I'm late!"), 10);
// A very heavy loop
for(let i = 0; i < 1000000000; i++) {}
```

**Code Explanation:**

- `setTimeout(..., 10);`: Registers a 10ms timer with the Web API.
- `for(...)`: This is a "blocking" loop. It stays on the Call Stack for much longer than 10ms.
- **Native Functionality:** After 10ms, the browser moves the callback to the **Task Queue**. However, because the Call Stack is busy with the `for` loop, the Event Loop cannot move the callback to the stack yet.
- **Connection:** The 10ms you provide is a **minimum time** until the task is queued, not a **guaranteed time** until it is executed.

---

### 3. The Microtask Queue (Promise Priority)

**Direct Answer:** Promises use a different, higher-priority queue called the **Microtask Queue**. This queue is dedicated to `.then()`, `.catch()`, and `.finally()` callbacks. The Event Loop prioritizes microtasks over regular tasks: it will empty the **entire** Microtask Queue before it allows even a single item from the Task Queue to run.

**Example: The Priority Race**

```js
setTimeout(() => console.log("Task Queue (Timer)"), 0);
Promise.resolve().then(() => console.log("Microtask Queue (Promise)"));
```

**Code Explanation:**

- `setTimeout(..., 0)`: The 0ms timer finishes instantly and puts its callback in the **Task Queue**.
- `Promise.resolve().then(...)`: The promise resolves instantly and puts its callback in the **Microtask Queue**.
- **Native Convention:** When the stack is empty, the Event Loop checks the Microtask Queue first.
- **Result:** "Microtask Queue (Promise)" logs first, even if the timer was registered first, because the Event Loop ensures the Microtask Queue is entirely empty before moving to the Task Queue.

### 4. The Render Queue and UI Fluidity

**Direct Answer:** The browser tries to repaint (render) the screen every **16.6 milliseconds** to maintain a smooth 60 FPS. Rendering also behaves like a queue that must wait for the Call Stack to be empty. However, the **Render Queue** has a higher priority than the Task Queue. If you "block" the stack with heavy synchronous code, the browser cannot render, causing the UI to freeze or become "janky".

**Example: Non-Blocking UI**

```js
// This freezes the UI during the loop
function block() { while(true) {} }

// This allows the browser to render between steps
function nonBlock() {
  setTimeout(nonBlock, 0);
}
```

**Code Explanation:**

- `while(true) {}`: This stays on the stack forever. The Event Loop can never pick up a render task, so the browser freezes.
- `setTimeout(nonBlock, 0);`: This calls a function, registers it as a Task, and pops it off the stack. This creates a "gap" where the stack is empty.
- **Connection:** During that tiny gap, the Event Loop can prioritize a **Render Task** to update the screen before picking up the next `nonBlock` task from the queue.

### Revision Summary: The Event Loop & Runtime Architecture

**Idea** - The Call Stack & Blocking **Explanation** - A single-threaded record of function calls. If a function is slow, it "blocks" the stack, preventing other code and UI rendering from occurring.

```js
function foo() { foo(); } // Blows the stack
```

`foo` calls itself until the browser hits a limit and kills the process to prevent a total crash.

**Idea** - Web APIs (The Threads) **Explanation** - Background threads provided by the browser (not the JS engine) for timers, network requests, and DOM events.

```
setTimeout(cb, 1000);
```

`setTimeout` is a Web API. The JS engine hands the callback to the browser and immediately moves to the next line.

**Idea** - The Task Queue (Callback Queue) **Explanation** - The storage area for callbacks from Web APIs (Timers, Events). Items here wait for the Call Stack to be empty.

```
// [Callback1, Callback2] waiting for the stack
```

Callbacks are pushed here after the background task (like a timer) finishes.

**Idea** - The Microtask Queue (Promise Queue) **Explanation** - A high-priority queue specifically for Promise reactions. It is emptied entirely before the Event Loop looks at the Task Queue.

```js
promise.then(data => console.log(data));
```

The `.then` callback goes to the Microtask Queue. If a microtask schedules another microtask, it can "starve" the Task Queue by looping indefinitely.

**Idea** - The Event Loop & Render Priority **Explanation** - The coordinator that moves items from queues to the stack. It prioritizes Microtasks, then Renders (every 16ms), then Tasks.

```
// Priority: Call Stack > Microtask Queue > Render Queue > Task Queue
```

This hierarchy ensures promises resolve quickly and the UI stays smooth before regular timers or clicks are handled.

### Full Code Picture: The Priority Quiz

```js
console.log("1: Start"); // 1. Synchronous Stack

setTimeout(() => {
  console.log("2: Timer"); // 4. Task Queue (lowest priority)
}, 0);

Promise.resolve().then(() => {
  console.log("3: Promise"); // 3. Microtask Queue (emptied after stack)
});

// A small synchronous task to ensure stack is occupied briefly
console.log("4: End"); // 2. Synchronous Stack

// Final Result Log Order: 1, 4, 3, 2
```

**Explanation:**

1. **"1: Start"** and **"4: End"** run immediately because they are synchronous.
2. The **Microtask Queue** has **"3: Promise"**. The Event Loop sees an empty stack and pushes this first.
3. The **Task Queue** has **"2: Timer"**. The Event Loop only pushes this after the Microtask Queue is completely empty.
4. The browser is able to **Render** between Step 2 and 3 if needed because the stack is empty.
