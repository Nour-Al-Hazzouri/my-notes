# What are these notes about?

# What this project taught me
During my time on this project, I quickly realized that working with modules is not the same as building the standard vanilla websites using HTML, CSS, and JS. In such projects, the structure is defined in the HTML file with CSS for styling and JS for interactivity.
First, I thought that instead of 1 file, I just had to split my functions into different files and that's it, but then realized that this was 1 advantage of bundling, not the whole story.
From this experience, here's what I've compiled:

- **Brainstorming is as important as coding:** when working on a project, especially larger or more complex ones, thinking through how you might want to approach it will make all the difference in the world. Typing the code is, in simple terms, interpreting your ideas into a language the processor can understand.
- **Logic first, anything else later:** figuring out how to build the logic and making it functional at the command line takes priority. Starting with the interface or DOM might limit your approaches later. Start with the initial logic structure, test the results in the console, then start with the UI.  
- **Execution time difference matters:** working with webpack means creating multiple JS files to split large functions into smaller ones, so there's an execution time for each module. Depending on the project's complexity, having multiple files imported inside other files will result in milliseconds of difference in each module's execution timing, which might lead to unexpected results.
- **Have a module's pipeline:** a pipeline is basically when the output of a function is the input of another function. For modules, think how each module you create will be called by other modules, and what it will do. For example, I faced an issue when the module was getting executed before the necessary data was available, which had me changing how it was called to ensure correct timing.
- **Build first, refactor later:** trying to perfect each module immediately, or after each idea that seems better, will take forever and get you nowhere. Finish the functionality first, and after understanding how pieces connect, improve how they work.
- **Keep things as scoped as possible:** it's tempting to keep things outside of scope and call them from inside multiple functions, and while sometimes it works, it might cause trouble.
  When a variable or a function call is set globally inside a module, it will execute the moment that module is imported by other modules. But when scoped inside a function, the execution depends entirely on when that function is called, and as mentioned, while the execution time difference might be only in milliseconds, unexpected results are possible.
- **Stay hydrated (pun intended XD):** in case you're using `browserStorageAPI`, a.k.a. `localStorage`, saving objects related to classes will need a hydration process. This means that the saved data will be returned as regular data without connection to the properties and methods of its classes. The browser uses JSON to store data locally, which doesn't support functions. After getting and parsing the data, ensure you re-create it as a new object of the same class.
  This process might cause issues if references to objects in your codebase are done through array indexes or similar approaches, and will need a specific function to re-link these references. Using ids is always a better approach.
- **Logging and Devtools are your friends:** an effective way to check where your logic is failing is using `console.log()`. For even more complex problems, Chromium's Devtools will prove very useful when debugging, especially breakpoints to dive into and step through functions where you suspect the issue is.

# General advice and best practices
My focus in these notes was tailored specifically to working with different modules using webpack (as I haven't experienced different bundlers yet). But in the scope of each module, best practices that are applied regularly should also be included, such as:

- **Naming Conventions:** each variable and function name should be based on `camelCase` and be descriptive. A variable's name should tell you exactly what it holds, and a function's name should naturally let you know if it's a procedure (function with no returned value), or what it does, including parameters or return values.
- **Comments:** your code should have a sweet spot for comments. Using a lot of comments will overwhelm the code and files, but not using comments at all will cause confusion. Keep it clean, simple, and readable, and only comment when necessary.
- **Style the code:** having your code styled nicely is essential for its readability. It can be easily maintained using extensions.
- **Keep it simple:** implementing logic can be done through multiple ways. The simplest functional way is always better.
